## Section 2: High-Level Solution Architecture & Component Design
*Synthesized by Solution Architect Agent*

As Principal Solution Architect at MindMesh AI, I have engineered the following architecture blueprint. Given the 6-month delivery timeline and 100k DAU load, I have selected a **"Modular Monolith to Microservices-Ready"** approach. This minimizes operational complexity for the MVP while ensuring the system can decompose into microservices without architectural refactoring.

---

### 1. Architectural Style & Paradigms
*   **Recommended Style:** **Modular Monolith (Strategic Decomposition)**.
*   **Rationale:** Microservices introduce excessive DevOps overhead for an initial 6-month delivery. We will build domain-bounded modules within a single C# .NET Core deployment unit. This ensures high performance (in-process calls) while allowing individual domains (Identity, Core, Notification) to be extracted into independent services later.
*   **Core Principles:**
    *   **Domain-Driven Design (DDD):** Enforce strict separation of concerns via modules.
    *   **CQRS:** Segregate Command (Write) and Query (Read) models to optimize for 100k DAU.
    *   **Stateless Compute:** All application servers must be stateless to support GKE auto-scaling.

---

### 2. Core Component Topology
| Component | Responsibility | Interaction | State Management |
| :--- | :--- | :--- | :--- |
| **API Gateway** | Auth, Rate Limiting, Request Routing | HTTPS/TLS 1.3 | Stateless |
| **App Module (Core)** | Business Logic, Domain Events | Internal / gRPC | Postgres (Primary) |
| **Identity Service** | OIDC/OAuth2, JWT Issuance | HTTPS/OIDC | Redis (Sessions) |
| **Message Broker** | Asynchronous Task Orchestration | Pub/Sub (GCP) | Persistent Queue |
| **Read/Query DB** | Optimized projections for UI | SQL | Postgres (Read Replica) |

---

### 3. End-to-End Data Flow
*   **Synchronous Flow (Write):** Client -> API Gateway -> Auth Check -> Command Handler (Validation) -> Write DB (Transactional) -> Event Publish (Domain Event).
*   **Asynchronous Flow (Background):** Event Publisher -> GCP Pub/Sub -> Async Worker -> Secondary processing (e.g., Email, Analytics) -> Dead Letter Queue on failure.
*   **Read Path:** Client -> API Gateway -> Query Handler -> Redis Cache -> (if miss) -> Read Replica -> Return JSON.

---

### 4. Storage, Caching & Consistency
*   **Transactional Data:** Google Cloud SQL (PostgreSQL) located in `europe-west3` (Frankfurt).
*   **Caching:** Memorystore (Redis) for session state and high-frequency read results.
*   **Consistency Model:** 
    *   **Write Path:** Strong consistency (ACID) within the transaction boundary.
    *   **Read Path:** Eventual consistency (using read replicas for scalability) with a Max Lag of <200ms.

---

### 5. Security & Data Residency (GDPR - Germany)
*   **Residency:** All managed services (GCP Cloud SQL, Redis, GKE) restricted to `europe-west3` via Organization Policy Constraints.
*   **IAM:** Google Cloud Identity Platform integration. 
*   **Encryption:** 
    *   In-Transit: TLS 1.3 (End-to-end).
    *   At-Rest: AES-256 with Customer Managed Encryption Keys (CMEK) via Google KMS.
*   **Boundary:** API Gateway acts as the WAF/Security perimeter; private subnets for all databases.

---

### 6. Scalability & Resilience
*   **Auto-scaling:** GKE Horizontal Pod Autoscaler (HPA) triggered at 60% CPU/Memory utilization.
*   **Fault Tolerance:**
    *   **Resilience4j:** Implemented in the app for Circuit Breaking.
    *   **Retries:** Exponential Backoff on all external service calls.
    *   **Isolation:** Bulkhead pattern applied to prevent slow external APIs from exhausting thread pools.

### 8. Architectural Trade-offs & Anti-Patterns Avoided
*   **Avoided:** **Full Distributed Microservices.** While trendy, the inter-service communication latency and operational complexity would threaten the 6-month delivery timeline. We use "Service-ready" modules instead.
*   **Avoided:** **GraphQL.** While powerful, it introduces significant complexity in authorization and performance tuning for 100k DAU. We stick to structured REST/OpenAPI to ensure strict schema validation and caching control.
*   **Over-Engineering Safeguard:** No complex service mesh (Istio) initially. We use standard GCP Ingress and K8s services, deferring Service Mesh until "Day 2" traffic requires advanced traffic shifting.
