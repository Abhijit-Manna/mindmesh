Section 2: High-Level Solution Architecture & Component Design

Synthesized by Solution Architect Agent

As the Principal Solution Architect for MindMesh AI, I have designed the following System Architecture Blueprint. This design prioritizes a "Modular Monolith moving toward Service-Orientation" to balance the 4-month delivery timeline with the scalability requirements for 50,000 DAU.

1. Architectural Style & Design Rationale

  • Style: Modular Monolith using a "Vertical Slice" approach.
  • Rationale: Microservices introduce operational complexity (service discovery, distributed tracing, network latency) that risks the 4-month MVP deadline. A modular monolith allows for strict domain boundaries within a single codebase, facilitating rapid iteration while ensuring the system can be decomposed into microservices later without major refactoring.
  • Core Principles:
    • CQRS (Command Query Responsibility Segregation): Separation of write/read models to optimize database performance.
    • Stateless Compute: All application servers are stateless to facilitate horizontal scaling.
    • Idempotency: All state-changing API endpoints require Idempotency-Key headers.

2. Core Component Topology & Responsibility Matrix

Component Role & Responsibility Protocol State Strategy
API Gateway Auth enforcement, Rate Limiting, Request Routing HTTPS/gRPC Stateless
Application Logic Business logic, Domain Validation FastAPI / Node.js Stateless
Task Queue Asynchronous background jobs Redis / RabbitMQ Durable (Persistent)
Primary RDBMS Persistent transactional state SQL (PostgreSQL) ACID Compliant
Read Cache High-frequency query acceleration Redis Ephemeral (LRU)
Object Store Unstructured media/binary data S3 API Immutable

3. End-to-End Data Flow

  • Synchronous Path (e.g., User Profile Fetch):
    1. Client -> Route 53 (DNS) -> CloudFront (CDN) -> API Gateway.
    2. API Gateway validates JWT.
    3. Application Service queries Redis Cache (Cache Hit).
    4. If Cache Miss: Query PostgreSQL (Primary) -> Populate Cache -> Return response.
  • Asynchronous Path (e.g., AI Processing):
    1. Client posts request -> API Gateway -> Application Service.
    2. Service writes request to PostgreSQL (Pending status) + pushes job ID to Task Queue.
    3. Worker process consumes job -> Executes AI task -> Updates PostgreSQL.
    4. Client polls or receives Webhook notification of completion.

4. Storage, Cache & Data Boundaries

  • Transactional Data: PostgreSQL (Multi-AZ RDS). Consistency: Strong Consistency (ACID).
  • Caching Layer: Elasticache (Redis). Consistency: Eventual (Cache-Aside pattern).
  • Audit/Logs: CloudWatch Logs + S3 Glacier for long-term compliance.
  • Data Residency: All AWS resources deployed exclusively to us-east-1 (N. Virginia), enforced via AWS IAM Service Control Policies (SCPs).

5. Security Architecture

  • IAM & Auth: OAuth2/OIDC via AWS Cognito or Auth0. JWTs issued with 15-min expiry; silent refresh pattern implemented.
  • Network: All services reside in private subnets within a VPC. Only API Gateway/Load Balancers are internet-facing.
  • Encryption: TLS 1.3 for in-transit data; AWS KMS (AES-256) for at-rest storage.
  • WAF: AWS WAF attached to CloudFront to block SQLi, XSS, and bot traffic.

6. Scalability, Resilience & Fault-Tolerance

  • Auto-Scaling: Target Tracking Scaling Policies based on CPU utilization (>60%) and Request Count per Target.
  • Fault Tolerance:
    • Circuit Breaker: Applied to external API calls to prevent cascading failures.
    • Retry Policy: Exponential Backoff (jittered) for transient network failures.
    • DLQ (Dead Letter Queues): Failed background jobs routed to SQS DLQ for manual inspection.
  • Peak Load: 2,500 req/sec handled by horizontal scaling of FastAPI nodes across 3 Availability Zones.

8. Architectural Trade-offs & Anti-Patterns Avoided

  • Avoided Microservices: We explicitly avoided a microservices architecture to prevent "distributed monolith" syndrome and operational overhead during the 4-month build phase.
  • Avoided NoSQL for Core Domain: While NoSQL is trendy, we chose PostgreSQL for critical business data to ensure referential integrity and support for complex reporting queries without data duplication.
  • Deferred: Advanced Service Mesh (Istio/Linkerd) and Multi-Region Active-Active replication have been deferred until post-MVP, as these are unnecessary for the current traffic profile and would severely impact the development velocity.
