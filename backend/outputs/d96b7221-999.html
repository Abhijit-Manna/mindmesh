9. High-Level Solution Architecture

As Principal Solution Architect at MindMesh AI, I have designed this blueprint for a production-grade MVP. Given the 4-month timeline and the 10,000 DAU scale, I have selected a Modular Monolith approach.

This provides the velocity of a monolith with the clean boundaries of microservices, allowing for a seamless transition to a distributed architecture later without the operational overhead of managing service discovery and complex inter-service communication (gRPC/Service Mesh) during the MVP phase.

1. Architectural Style & Design Rationale

  • Style: Modular Monolith (Node.js/TypeScript).
  • Rationale: Microservices introduce excessive DevOps overhead for a 4-month MVP. The Modular Monolith enforces strict domain boundaries through folder-level encapsulation and internal APIs, ensuring code quality without the "distributed system tax."
  • Principles:
    • CQRS (Light): Separate command (write) models from query (read) models within the application layer.
    • Stateless Compute: All application servers remain stateless, offloading session state to Redis.
    • Idempotency: Implement idempotency keys on all write operations to handle network retries.

3. Data Flow & Request Lifecycles

  • Synchronous Flow (Read/Write): Client → CDN → API Gateway → App (Domain Service) → Primary DB → Client.
  • Asynchronous Flow (Background Task): App (Domain Service) → Message Queue → Worker Process → External Service/Data Sink.
  • Sequence:
    1. Gateway validates JWT.
    2. Request routed to the specific domain module.
    3. Transactional change written to PostgreSQL.
    4. Successful commit triggers an Event (via local Event Bus or Message Queue).
    5. Cache invalidated/updated as a side-effect.

4. Storage, Cache & Data Boundaries

  • Primary Database: PostgreSQL (Single Primary, Read-Replica for scale).
  • Cache: Redis Cluster for session state and hot-path API responses.
  • Consistency Model:
    • Primary DB: ACID (Strong consistency).
    • Cache: Eventual consistency (Cache-aside pattern).

5. Security Perimeter & India Residency

  • Data Residency: All AWS/GCP/Azure resources will be deployed to the ap-south-1 (Mumbai) region. Database encryption at rest using AWS KMS (Customer Master Key).
  • Identity: OAuth2/OIDC using a managed provider (e.g., Auth0 or Cognito). JWTs issued with short TTL (15 mins) and rotating refresh tokens.
  • Network: VPC with private subnets for DB/Cache. API Gateway acts as the only public ingress. TLS 1.3 mandated for all connections.

6. Resilience, Scalability & Failover

  • Scalability: Horizontal Pod Autoscaler (HPA) targeting 60% CPU utilization.
  • Resilience:
    • Circuit Breaker: Applied to all external API integrations.
    • Retry Pattern: Exponential backoff for transient failures in downstream services.
    • DLQ: Any event failing processing > 3 times is routed to a Dead Letter Queue for manual audit.

8. Architectural Trade-offs & Anti-Patterns Avoided

  • Avoided: Service Mesh (Istio/Linkerd). Adds too much complexity for an MVP. We use the API Gateway for basic routing and monitoring.
  • Avoided: Distributed Transactions (SAGA pattern). Complexity is too high. We keep transactions within a single PostgreSQL instance for the MVP.
  • Avoided: Kubernetes (for initial infra). Started with Managed Container Services (e.g., AWS App Runner or Fargate) to reduce "Cluster Ops" burden.
  • Rationale: By avoiding these, we deliver within 4 months while maintaining a "Refactor-Ready" codebase.

3. Cross-Discipline Technical Consistency & Harmonization Audit

  • Protocol Uniformity: All microservices communicate via gRPC for internal low-latency orchestration and REST/JSON for external consumer-facing endpoints.
  • Schema Governance: A shared Schema Registry ensures that service versioning (e.g., Patient record updates) does not break downstream billing or pharmacy dependencies.
  • Deployment Alignment: The 4-month delivery window is harmonized with a CI/CD pipeline leveraging ArgoCD. The "4-week per feature-set" sprint cadence ensures the architecture evolves iteratively without manual configuration drift.
  • Data Integrity: Transactional consistency is maintained via the Saga Pattern (Orchestration-based) to manage distributed transactions across microservices.

4. Data Residency, Security & Regulatory Compliance (India Focus)

Given the mandate for Indian data residency, the following controls are implemented:
* Infrastructure Hosting: All primary, replica, and backup storage instances are pinned to the ap-south-1 (Mumbai) or ind-central-1 regions of the chosen Cloud Service Provider.
* DPDP Compliance: Every PII field is encrypted at rest using AES-256 with customer-managed keys (CMK). We implement mandatory "Right to be Forgotten" workflows, allowing for automated data purging via the orchestration layer.
* Network Isolation: Services are housed in private subnets with no direct public internet access. Security Groups strictly enforce identity-based access control (IAM roles) rather than IP-based rules.
* Audit Trail: Immutable audit logs are exported to a dedicated, write-once-read-many (WORM) storage bucket, ensuring compliance with Indian medical record preservation standards.

5. Total Cost of Ownership (TCO) & Sizing Considerations

Operational Sizing (10k DAU MVP):
* Compute: 4 Nodes (c6g.large) running in an EKS cluster with HPA enabled to scale from 2 to 10 pods during peak hours.
* Storage: 2TB Provisioned IOPS SSD for PostgreSQL RDS with multi-AZ replication.
* Data Transfer: Estimated 500GB/month egress (internal to Mumbai region).

Optimization Strategy:
1. Serverless for Bursty Workloads: Shift notification and report-generation tasks to Lambda/Cloud Functions to minimize idle CPU costs.
2. Tiered Storage: Move historical patient records older than 12 months to Cold Storage (Infrequent Access) to reduce storage costs by ~60%.
3. Savings Plans: Commit to 1-year compute savings plans for the baseline (min-capacity) nodes to realize ~30% cost efficiency.

Day-2 Operations Recommendation:
Implement Prometheus/Grafana observability early. As the system scales beyond 20k DAU, consider moving from a primary/replica RDBMS setup to a distributed sharded database approach to prevent write-bottlenecks.
