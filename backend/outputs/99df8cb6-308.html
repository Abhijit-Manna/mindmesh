Section 2: High-Level Solution Architecture & Component Design

Synthesized by Solution Architect Agent

This architectural blueprint defines the foundation for a high-concurrency, GDPR-compliant platform deployed on Google Cloud (GCP) in the europe-west3 (Frankfurt) region.

1. Architectural Style & Design Rationale

Style: Modular Monolith (moving toward Microservices via "Vertical Slicing")
* Rationale: With a 6-month delivery timeline, a full-blown microservices architecture introduces excessive operational complexity (distributed transactions, service discovery, mesh management) that risks the MVP.
* Design Principles:
* Domain-Driven Design (DDD): Define clear bounded contexts within the code (e.g., Identity, Transaction, Reporting) to allow for effortless extraction into independent services later.
* Stateless Compute: All application instances will be stateless, relying on externalized caches (Redis) and DBs.
* Asynchronous Processing: Offload non-blocking operations to Cloud Pub/Sub to ensure high throughput and low latency.

3. End-to-End Data Flow

  • Synchronous Flow (Read/Write): Client → HTTPS Load Balancer → Apigee → Spring Boot (App Service) → Primary DB (Cloud SQL). Read-heavy operations verify the Redis cache before querying SQL.
  • Asynchronous Flow (Background Jobs): Spring Boot → Pub/Sub Topic → Cloud Functions (Worker) → External Webhooks or Analytics Engine. This decoupling ensures the main request thread is never blocked.

4. Storage, Caching & Data Boundaries

  • Transactional Boundary: PostgreSQL (Cloud SQL) with Read Replicas.
  • Cache Strategy: Multi-level caching. Global cache (Redis) for session/frequent objects; L1 local cache for static configuration.
  • Consistency Model:
    • Transactional: ACID compliance for user/transactional data.
    • Eventual: Analytics and background audit logs utilize eventual consistency.

5. Security Architecture & Data Residency

  • Identity: OIDC/OAuth2 via Google Identity Platform or Keycloak deployed in GKE.
  • Data Residency: All regional resources (europe-west3) are locked via GCP Organization Policies. No cross-region replication enabled for PII.
  • Encryption: TLS 1.3 in transit; AES-256 (customer-managed encryption keys - CMEK) at rest.
  • Perimeter: VPC Service Controls to prevent data exfiltration. Private Google Access ensures no traffic traverses the public internet.

6. Scalability & Resilience

  • Auto-scaling: GKE Horizontal Pod Autoscaler (HPA) triggers at 60% CPU/Memory utilization.
  • Resilience Patterns:
    • Circuit Breakers: Resilience4j implementation to stop cascading failures during downstream service outages.
    • Dead-Letter Queues (DLQ): Every Pub/Sub message has a retry policy (3 attempts) before being routed to a DLQ for investigation.
    • Rate Limiting: Managed at the API Gateway level to prevent DDoS and resource exhaustion.

8. Architectural Trade-offs & Anti-Patterns Avoided

  • Avoided Micro-Frontend: For a 6-month timeline, we opted for a monolithic Angular application to avoid the extreme build-pipeline complexity of Micro-frontends.
  • Avoided Multi-Cloud: To meet the timeline and residency constraints, we avoided abstraction layers (e.g., Terraform-heavy multi-cloud setup) and focused purely on GCP-native managed services to speed up deployment.
  • Avoided CQRS/Event Sourcing: While powerful, these patterns introduce high cognitive load and debugging complexity. We opted for standard CRUD with indexed relational storage, keeping Event Sourcing as a potential Phase 2 evolution.
