1. Executive Problem Definition & Business Context

Problem Breakdown

Modern B2B supply chains, particularly in temperature-sensitive (cold-chain) and high-volume freight logistics, suffer from severe operational silos, data fragmentation, and a lack of real-time visibility. Stakeholders—ranging from enterprise shippers and logistics service providers (LSPs) to warehouse operators and fleet drivers—operate on disparate systems, leading to:
* Blind Spots in Transit: Inability to track live GPS telemetry and IoT sensor data (e.g., temperature, humidity, shock) simultaneously, causing massive spoilage and cargo loss in pharmaceutical and perishable food supply chains.
* Inefficient Fleet & Route Utilization: Static routing and manual dispatching fail to adapt dynamically to traffic congestion, road closures, or sudden demand spikes, escalating fuel consumption and delivery delays.
* Inventory Bullwhip Effects: Discrepancies between warehouse inventory levels and inbound freight statuses result in stockouts, overstocking, and demurrage charges at fulfillment hubs.
* Communication Friction: Fragmented operational workflows between dispatchers, drivers, and warehouse staff create administrative bottlenecks and slow exception resolution.

Market Context & Core Value Proposition

Operating within the rapidly digitizing Indian logistics and supply chain ecosystem, MindMesh AI provides a unified, real-time B2B supply chain visibility and orchestration platform.
* Value Proposition: MindMesh AI bridges the gap between physical transportation and digital inventory control by fusing real-time GPS tracking, IoT cold-chain telemetry, predictive route optimization, and automated warehouse forecasting into a single operational glass pane.
* Core Business Impact: Minimize cargo spoilage, slash transit times and fuel costs, optimize inventory carrying costs, and automate exception management to guarantee SLA compliance for enterprise shippers.

Success Metrics (KPIs)

  • On-Time In-Full (OTIF) Delivery Rate: Target increase from an industry average of 78% to $\ge 94\%$.
  • Cold-Chain Excursion Resolution Time: Reduction in time-to-detect and time-to-mitigate temperature excursions from $>45$ minutes to $<5$ minutes.
  • Fleet Utilization & Empty Running Miles: Reduction in empty return legs by $18\%$.
  • Operational Efficiency: $35\%$ reduction in manual dispatcher intervention per trip via automated dispatching.

  6. The Go service extracts the context and checks Redis for the X-Idempotency-Key. If present, it returns the cached result.

5. Database, Caching & Data Store Architecture

5.1 Relational Database Architecture (Aurora PostgreSQL)

Schema Design & Partitioning Strategy

To handle high-volume event logs and transactional telemetry at peak 2,500 RPS:
1. Time-Series / Range Partitioning: Audit logs, user activity traces, and billing logs are declaratively range-partitioned by month (partition_key: created_at).
2. Connection Pooling: Go microservices use native pgxpool alongside AWS RDS Proxy. RDS Proxy maintains a warm pool of database connections, preventing thread exhaustion on the Aurora database during rapid pod scaling events on EKS.
3. Primary Key Strategy: Distributed UUIDv7 (Timestamp-first UUIDs) is enforced across all tables. This eliminates B-Tree index page fragmentation associated with random UUIDv4 keys while avoiding sequential ID enumeration vulnerabilities.

-- Architectural Reference: Optimized UUIDv7 Table Schema with Partitioning
CREATE TABLE user_events (
    event_id UUID NOT NULL DEFAULT gen_random_uuid_v7(),
    user_id UUID NOT NULL,
    event_type VARCHAR(64) NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (event_id, created_at)
) PARTITION BY RANGE (created_at);

-- Indexes for Query Performance
CREATE INDEX idx_user_events_user_id ON user_events(user_id, created_at DESC);
CREATE INDEX idx_user_events_payload_gin ON user_events USING GIN (payload);

5.3 Asynchronous Messaging & Queue Architecture

Message Processing Guarantees

  • Delivery Semantics: At-least-once delivery guaranteed.
  • Idempotency Strategy: All consumer microservices implement an Idempotent Consumer Pattern. Each event contains a unique event_id (UUIDv7). Consumers run an atomic check-and-set in Redis before processing:
    go SET idempotency:event_id "PROCESSING" NX EX 300
    If key exists, the message is ignored as duplicate.

High-Throughput Topology (2,500 RPS Peak Capacity)

  • Dead Letter Queue (DLQ): Messages failing processing after 3 retry attempts with exponential backoff (2s, 8s, 32s) are moved to an isolated DLQ (mindmesh-dlq-service-name). Alerts trigger on CloudWatch metrics when DLQ message count > 0.
  • Backpressure Management: Workers maintain dynamic worker-pool sizes (gamma-zero/workerpool) governed by AWS SQS Queue Depth metrics (ApproximateNumberOfMessagesVisible).

4. Zero-Downtime Release & Database Migration Strategy

4.1 Zero-Downtime Deployment via Argo Rollouts

MindMesh AI uses Argo Rollouts for Kubernetes to manage declarative Blue/Green and Canary deployments.
* Traffic Splitting: Integrated directly with AWS ALB and AWS Load Balancer Controller to shift weights dynamically (10% -> 25% -> 50% -> 100%).
* Automated Health Analysis: During each traffic shift phase, Prometheus metrics (http_request_duration_seconds and http_requests_total{status=~"5.*"}) are queried. If error rates exceed 0.5% over a 2-minute sliding window, Argo Rollouts triggers an automatic rollback to the stable version.

4.2 Backward-Compatible Database Migrations (Expand/Contract Pattern)

To eliminate downtime during PostgreSQL schema modifications, database migrations strictly follow the Expand/Contract (Parallel Run) pattern:
1. Expand Phase:
* Add a new nullable column or create a new table alongside the old one.
* Deploy dual-write application logic (writes to both old and new schemas, reads from old schema).
* Backfill historical data asynchronously via background worker tasks.
2. Migrate Phase:
* Switch application read traffic to the new schema/column.
* Remove dual-write code and keep only single-write to the new schema.
3. Contract Phase:
* In a subsequent release (at least 2 weeks later), drop deprecated columns or tables.
