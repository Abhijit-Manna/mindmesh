Solution Architecture Document: B2B Recharge Platform

1. Executive Summary

This architecture provides a scalable, secure, and compliant foundation for a B2B Recharge Platform, designed for the AWS India (Mumbai) Region. Leveraging a modular microservices approach with Java Spring Boot, this design ensures high transactional integrity and meets the 4-month MVP timeline.

2. Major System Components

Core Backend (Java Spring Boot)

  • Identity Service: Manages Partner/Admin registration, authentication (JWT), and Role-Based Access Control (RBAC).
  • Wallet Service: Manages ledger integrity, balance lookups, and transactional debits/credits.
  • Recharge Service: Orchestrates communication with external aggregators and tracks transaction status.
  • Notification Service: Manages alerts for low balances or transaction updates.

Frontend (Angular)

  • Partner Portal: Dashboard for balance checks, recharge initiation, and history.
  • Admin Console: Management of partners, transaction oversight, and manual balance reconciliation.

Data Layer

  • Primary Database: Amazon RDS (PostgreSQL) for transactional data (ACID compliance is critical for wallet logic).
  • Cache: Amazon ElastiCache (Redis) for session management and fast balance lookups.

3. Communication & Data Flows

  • Internal Communication: RESTful APIs over HTTPS/TLS 1.3 for service-to-service interaction.
  • Data Flow:
    1. Recharge Request: Partner initiates request → Identity Service validates session → Wallet Service locks balance → Recharge Service calls Provider API.
    2. Callback/Reconciliation: External Provider sends webhook response → Recharge Service updates record → Wallet Service performs reconciliation check.
  • Asynchronous Processing: Amazon SQS is used to queue recharge requests to handle bursts in traffic and ensure 99.9% availability, preventing transaction timeouts.

4. External Integrations

  • Recharge Aggregators: Secure HTTPS REST APIs provided by third-party telecom/DTH aggregators.
  • Banking Gateways: (Future/Manual for MVP) Integration for automated balance top-ups.

5. Security & Reliability

  • Security:
    • Data at Rest: AWS KMS (Key Management Service) for database and volume encryption.
    • Data in Transit: TLS 1.3 for all communications.
    • Compliance: AWS WAF (Web Application Firewall) to protect against common web exploits.
  • Reliability:
    • Multi-AZ Deployment: RDS and EC2/ECS across multiple Availability Zones in the Mumbai region for high availability.
    • Auditability: Centralized logging via Amazon CloudWatch, capturing every API call and transaction state change for compliance.

6. Scalability

  • Horizontal Scaling: Use of Amazon ECS (Elastic Container Service) with Auto Scaling Groups. The stateless nature of Spring Boot services allows the system to scale based on CPU/Memory utilization to handle the 10,000 DAU load effectively.

8. Infrastructure Strategy (India Region)

  • Region: ap-south-1 (Mumbai).
  • Data Residency: Strict configuration of VPC and RDS instances to reside solely within the Mumbai region; VPC Flow Logs enabled for audit compliance.
  • Deployment: CI/CD pipeline using AWS CodePipeline and CodeBuild to automate testing and deployments to ensure the 4-month deadline is met.

9. Justification of Technology Stack

  • Java Spring Boot: Chosen for its robust support for transaction management (Spring Data JPA) and enterprise-grade security libraries (Spring Security), essential for financial ledger integrity.
  • Angular: Chosen for its modular architecture and strong two-way data binding, allowing rapid development of complex dashboard views required by administrators and partners.
  • AWS: Provides the most mature infrastructure in India, ensuring strict compliance with local data residency laws and offering high-availability primitives out of the box.

Detailed Justifications

1. Backend: Java Spring Boot 3.x

  • Why: Spring Boot is the industry standard for financial applications. Its built-in Spring Transaction Management is critical for ensuring the "Wallet Management" (FR02) requirement, where Atomicity is non-negotiable.
  • Requirement Addressed: Transaction integrity and high-concurrency handling.
  • Trade-off: Longer initial setup time than Node.js, but provides superior long-term maintainability for complex financial logic.

2. Frontend: Angular

  • Why: Angular’s strict structure and TypeScript usage are ideal for large-scale enterprise dashboards (FR05). Its built-in support for Form validation is vital for the transactional input requirements.
  • Requirement Addressed: Secure, state-driven dashboards for Admins and Partners.

3. Database: Amazon RDS for PostgreSQL

  • Why: PostgreSQL is the most reliable relational database for financial ledger operations. Multi-AZ deployment ensures 99.9% availability.
  • Data Residency: Configured strictly in ap-south-1 to meet Indian data residency requirements.

4. Caching: Amazon ElastiCache (Redis)

  • Why: Essential to reduce DB load for frequent operations like "Wallet Balance" lookups (FR02) which occur on every dashboard refresh.
  • Requirement Addressed: Performance (< 2s processing time).

5. Messaging/Event System: Amazon SQS

  • Why: Decouples the "Recharge Execution" from the UI. If a provider's API experiences latency, the recharge request remains safe in a queue, allowing the system to retry automatically without crashing the user session.
  • Requirement Addressed: Reliability and asynchronous processing.

6. Authentication: Spring Security + JWT

  • Why: Provides secure, stateless token-based authentication. Using JWT allows the system to easily handle RBAC (Role-Based Access Control) between Admins and Partners.
  • Requirement Addressed: Secure Partner Registration (FR01) and Admin Access.

7. Infrastructure: AWS ECS (Fargate)

  • Why: Fargate removes the overhead of managing EC2 instances, allowing the team to focus purely on the application code to meet the 4-month deadline. It scales horizontally based on traffic.
  • Requirement Addressed: 10,000 DAU scalability.

8. Monitoring & Logging: CloudWatch & AWS X-Ray

  • Why: CloudWatch provides the centralized logs required for Auditability. X-Ray is critical for tracing a transaction across microservices to identify where a bottleneck occurs (e.g., if a 3rd party provider is slow).
  • Requirement Addressed: Auditability and Performance Monitoring.

9. Testing: JUnit 5, Mockito, & Cypress

  • Why: Unit tests (JUnit/Mockito) are non-negotiable for wallet calculations. Cypress provides automated End-to-End (E2E) testing for the critical "Recharge" flow, preventing regressions.
  • Timeline Impact: Automated testing is the only way to meet the 4-month goal while ensuring stability.
